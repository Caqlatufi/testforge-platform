# TestForge AI 证据诊断 验收方案

> 验收只认真实 Provider 执行结果与证据。本文验证 AI-S1～AI-S5，其中相同 requestKey 的并发请求必须只触发一次 Provider 调用。

## 1. 验收流程

### 1.1 验收准备

| 项目 | 要求 |
|---|---|
| 验收版本 | 固定 app、Provider 适配器、模型配置和输出 Schema 版本 |
| 验收环境 | 已登录的真实 Provider 可用，同时准备可控故障 Provider |
| 账号与数据 | 准备含完整证据的失败报告、历史成功诊断和固定 requestKey |
| 故障注入 | 可模拟未登录、繁忙、超时、进程失败及非法 evidenceId/JSON |
| 证据目录 | 保存脱敏输入、Provider 元数据、原始输出、校验结果和报告前后快照 |

### 1.2 执行顺序

```mermaid
flowchart LR
    A[检查 Provider readiness] --> B[组装失败证据]
    B --> C[真实 Provider 诊断]
    C --> D[校验 Schema 与 evidenceId]
    D --> E[验证幂等复用和强刷]
    E --> F[注入 Provider 故障]
    F --> G[核对权威报告不变]
    G --> H[验证页面降级]
```

## 2. 流程验收场景

| 场景编号 | 覆盖的成功标准 | 前置条件 | 操作 | 预期结果 | 已知相邻影响检查 | 证据要求 |
|---|---|---|---|---|---|---|
| AI-AC-01 | AI-S1 | 真实 Provider 已登录，失败报告证据完整 | 发起诊断并逐项反查 evidenceId | 返回符合 Schema 的结构化诊断，所有引用均来自输入证据 | 报告页展示的分类、建议和证据与 API 一致 | readiness、脱敏输入摘要、原始输出、校验记录、页面截图 |
| AI-AC-02 | AI-S2 | 已完成一次成功诊断 | 重放 requestKey、对相同证据发新请求，再以新 key 强刷 | 重放不重复调用；相同证据可复用；强刷生成新记录 | 历史成功诊断仍可查询 | Provider 调用计数、诊断记录、响应中的 reused 标记 |
| AI-AC-03 | AI-S3 | 故障 Provider 可控 | 分别注入未登录、繁忙、超时、进程失败和非法输出 | 每类失败可区分、可追踪，非法输出不进入成功结果 | readiness 和页面提示与故障类型一致 | 各类响应、状态记录、日志 traceId |
| AI-AC-04 | AI-S4 | 已保存权威报告快照 | 在所有诊断失败场景前后比较报告 | 报告、通过率和确定性失败分类完全不变 | Run/Task/TestResult 无写入变化 | 前后报告 diff、数据库核对、审计日志 |
| AI-AC-05 | AI-S5 | Provider 不可用且有历史成功诊断 | 打开报告页并尝试新建诊断 | 原报告和历史诊断可查看，新建动作禁用或失败原因可读 | 报告附件和历史记录仍可访问 | 页面截图/录屏、API 响应 |

## 3. 并发验收

| 项目 | 验收口径 |
|---|---|
| 并发不变量 | 同一 reportId + requestKey 只产生一条权威诊断和一次 Provider 调用 |
| 负载模型 | 20 个客户端同时提交完全相同的 reportId、requestKey 和 forceRefresh=false |
| 并发量与持续时间 | 20 并发请求，连续执行 5 轮 |
| 执行步骤 | 清理本轮 key，设置 Provider 调用计数，栅栏同时发起请求，核对响应和持久化记录 |
| 达标指标 | 每轮 Provider 调用数=1、权威诊断记录数=1；其余请求返回同一结果或明确处理中 |
| 已知相邻影响检查 | 报告内容不变；其他 reportId 的诊断请求可正常处理 |
| 证据要求 | 并发脚本、请求/响应汇总、Provider 调用计数、数据库唯一记录和日志 |

| 场景编号 | 覆盖的成功标准 | 并发场景 | 预期结果 | 证据要求 |
|---|---|---|---|---|
| AI-CC-01 | AI-S2 | 20 个相同幂等请求并发提交，连续 5 轮 | 每轮至多一次 Provider 调用且只有一条权威结果 | 每轮调用计数、结果 ID 集合、数据库记录 |
