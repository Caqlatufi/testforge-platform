# TestForge YAML Case 与托管测试资源验收方案

## 1. 验收流程

### 1.1 验收准备

| 项目 | 要求 |
| --- | --- |
| 验收版本 | 固定后端、前端、Worker、CLI 和 OpenAPI Commit |
| 验收环境 | TestForge API、MySQL、Console、一个进程 Worker、一个 Airtest Worker |
| 测试数据 | 一个 Project、一段内联 pytest、一个 `.py`、一个含图片的 `.air.zip`、一个危险 ZIP |
| 证据目录 | `acceptance/evidence/yaml-case-assets/` |

### 1.2 执行顺序

```mermaid
flowchart LR
    A[上传脚本/Airtest 包] --> B[插入并校验 YAML]
    B --> C[创建 Case]
    C --> D[加入并发布 Workflow]
    D --> E[Worker 下载执行]
    E --> F[修改 Case 后再次执行同一Workflow]
    F --> G[核对两次Run快照]
    G --> H[CLI 与负向场景]
```

| TA-AC-10 | TA-S2、TA-S6 | 准备零入口和两个 `.air` 根的 ZIP | 分别上传 | 返回稳定 400；不创建 Asset，也不允许通过下拉选择主入口 | 单 `.air` 根加辅助脚本可上传 | 响应与 Asset 数量 |

## 3. 并发验收

| 项目 | 验收口径 |
| --- | --- |
| 并发不变量 | 同一项目相同内容只产生一个逻辑 Asset；响应均指向同一 URI/摘要 |
| 负载模型 | 20 个并发上传请求使用同一文件和 projectId |
| 并发量与持续时间 | 20 请求一次突发，重复 3 轮 |
| 执行步骤 | 并发 multipart 上传，收集状态、assetId、sha256 后查询数据库 |
| 达标指标 | 60 请求无 5xx；每轮所有成功响应 assetId 相同；唯一记录数为 1 |
| 已知相邻影响检查 | Case validate 可立即引用该 Asset |
| 证据要求 | 请求结果、日志、数据库计数 |

| 场景编号 | 覆盖的成功标准 | 并发场景 | 预期结果 | 证据要求 |
| --- | --- | --- | --- | --- |
| TA-CC-01 | TA-S2、TA-S6 | 同内容并发上传 | 唯一 Asset，无半记录和 5xx | 原始输出、数据库与日志 |
