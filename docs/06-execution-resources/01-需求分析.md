# TestForge 执行资源与 Case 级调度需求分析

> 核心业务闭环：测试工程师维护 Case 时声明执行器和能力需求，发布 Workflow 时固化每个节点的资源契约；Test Job 执行到可运行节点后，平台按 Case 契约和目标系统动态分配容器或交互环境，执行结束释放资源并保存实际分配证据。

## 1. 目标

| 项 | 内容 |
| --- | --- |
| 目标用户/系统 | 测试工程师、Workflow 编排器、资源调度器、环境 Agent、平台管理员 |
| 触发场景 | 同一 Workflow 同时包含 API/脚本 Case 和 Windows、Android、iOS UI Case |
| 当前问题 | `resourceMode`、进程并发和设备并发被固化在 Task/Run/Test Job；Worker 同时表示队列消费者和机器代理；Environment、DeviceSlot 与资源池含义重叠，用户无法判断真实容量和等待原因 |
| 期望结果 | Case 声明执行能力，Workflow 声明依赖与会话范围，Test Job 不填写资源和并发；平台在节点就绪时生成资源申请，由统一调度器分配 Docker 沙箱或交互测试目标 |
| 业务价值 | 脚本任务按主机负载提高并发密度，UI 任务按真实桌面或设备容量排队；新增执行基座不改变 Test Job 与 Workflow 业务模型 |

## 2. 核心业务流程

| 步骤 | 执行者 | 动作 | 系统响应或状态变化 |
| --- | --- | --- | --- |
| 1 | 测试工程师 | 创建或编辑 Case，选择执行器、交互方式和必要能力 | Case 保存可复用的执行需求，不保存机器、资源池或并发数 |
| 2 | 测试工程师 | 将 Case/Fixture 编排进 Workflow 并发布 | 每个可执行节点固化 Case 版本、执行需求和可选会话范围 |
| 3 | 测试工程师 | 创建 Test Job，固定 Project、Commit、WorkflowVersion 和目标系统 | Test Job 不保存 `resourceMode`、进程并发、设备并发或具体环境 |
| 4 | 运行编排器 | 将依赖满足的 Workflow 节点转为可执行 Task | Resource Planner 结合 Case 需求、目标系统和平台策略生成 ResourceClaim |
| 5 | 调度器 | 固定数量的 Dispatcher Worker 消费待执行 Task | 为 Claim 原子分配满足能力和容量的 Provider/资源，并建立 Lease |
| 6 | Execution Provider | 无头脚本创建临时容器；UI 任务调用目标环境 Agent 和 Automation Driver | Attempt 保存 Provider、Environment、Agent、资源和运行时实例证据 |
| 7 | 运行编排器 | 接收结果、释放后继并回收 Lease | 当前 Task 收敛；下一批节点按实时资源继续调度 |
| 8 | 操作人员 | 查看资源与队列 | 页面展示计算容量、交互测试目标、等待 Case 及阻塞原因，不以注册 Worker 数量冒充容量 |

## 3. 关键规则

| 编号 | 规则 | 生效条件 | 影响的流程步骤 |
| --- | --- | --- | --- |
| CR-R1 | 资源需求归属于 Case；Test Job 只提供目标系统等运行上下文，不允许用户填写资源池或并发数 | Case/任务保存 | 1、3 |
| CR-R2 | Case 声明执行器、交互方式和能力，不声明具体 VM、设备或资源池 | Case 保存 | 1 |
| CR-R3 | Workflow 发布版本必须固化每个节点的执行需求；运行时不得读取已变化的 Case 最新配置 | Workflow 发布与执行 | 2、4 |
| CR-R4 | ResourceClaim 仅在节点满足依赖并准备执行时创建，默认在 Case Attempt 终态释放，不因 Workflow 中存在 UI Case 而提前占用整台环境 | 节点调度 | 4～7 |
| CR-R5 | `CASE` 是默认 Lease 作用域；需要连续共享登录态或应用状态时，由 Fixture/子流程声明 `SUBFLOW` 会话范围 | Workflow 编排 | 2、4～7 |
| CR-R6 | 不再使用“独占/非独占任务”分类；CPU、内存是可计量资源，桌面会话、模拟器和真机是容量通常为 1 的可分配资源 | 资源匹配 | 4～6 |
| CR-R7 | Dispatcher Worker 是控制面固定数量的通用队列消费者，不绑定 Windows/Android/iOS | 平台运行 | 5 |
| CR-R8 | Environment Agent 是随 VM/Node 存在的执行代理；Agent 可重启或替换，不是调度并发数量 | 环境注册与执行 | 5、6 |
| CR-R9 | 无头脚本优先通过 Container Provider 创建一次性沙箱；需要真实桌面、模拟器或真机的 Case 通过 Interactive Provider 分配目标资源 | Provider 选择 | 5、6 |
| CR-R10 | 实际并行度由已就绪 Workflow 节点、Dispatcher Worker、Provider 容量和实时资源共同决定，不由 Test Job 输入值决定 | 并发执行 | 4～7 |
| CR-R11 | Test Job 的目标系统与 Case 能力取交集生成 Claim；没有满足条件的 Provider 或资源时保持等待并展示稳定阻塞原因 | 资源规划 | 4、5、8 |
| CR-R12 | 旧 `PROCESS_POOL/EXCLUSIVE_DEVICE` 和旧并发字段仅用于兼容读取；新 Case、Workflow 和执行快照使用执行需求与 ResourceClaim | 兼容迁移 | 1～7 |
| CR-R13 | Environment 是一台可独立管理的 VM、Node 或设备宿主机；Environment Agent 是可替换的运行时进程，不把 Agent 数量当作容量 | 环境登记、Agent 注册 | 5、6、8 |
| CR-R14 | UI Case 通过 Automation Driver SPI 选择适配器；Airtest Adapter 支持 Windows、Android、iOS，并统一产出日志、截图和报告引用 | 交互执行 | 6、7 |
| CR-R15 | Case 未声明遗留 `parameters.platform` 或声明 `ANY` 时继承 Test Job 目标系统；只有 Case 显式平台与任务目标系统不同才拒绝 | Run 创建与资源规划 | 3～5 |
| CR-R16 | 资源容量必须按 `RUNNER_*` 能力分别计算；Airtest Agent 不得被计入 pytest-http 或 playwright-web 的可执行容量 | 资源总览与调度 | 5、8 |
| CR-R17 | HEADLESS Case 的等待文案必须指向兼容执行器或脚本槽；只有交互式 Case 才显示等待测试机 | 等待资源 | 5、8 |

## 4. 异常分支

| 编号 | 异常场景/触发条件 | 系统处理 | 用户或调用方可见结果 | 最终状态 |
| --- | --- | --- | --- | --- |
| CR-E1 | Case 显式平台或能力与 Test Job 目标系统冲突 | 启动前拒绝并定位 Workflow 节点；缺省平台不视为冲突 | 显示不兼容的 Case、能力和目标系统 | 不创建执行 Task |
| CR-E2 | 当前没有满足 Claim 的 Provider 或资源 | Task 保持等待，不创建有效 Attempt | 显示 `NO_MATCHING_PROVIDER` 或 `CAPACITY_EXHAUSTED` | 等待资源 |
| CR-E3 | Container 创建失败 | 释放 Claim；按基础设施失败策略重试 | 时间线显示 Provider 错误和重试 | 新 Attempt 或失败终态 |
| CR-E4 | Agent 失联或 Lease 过期 | 当前 Attempt LOST，回收资源并重新规划 | 显示原环境和重新分配记录 | 新 Attempt 继续或失败 |
| CR-E5 | 同一交互资源被并发申请 | 原子 Lease 只允许一个 Claim 成功 | 失败方继续排队且不启动 Driver | 不双占 |
| CR-E6 | SUBFLOW 会话中的前置节点失败 | 终止会话后续执行并释放整组 Lease | 子流程显示失败节点和释放原因 | 子流程收敛 |

## 5. 本期包含

> 本节采用白名单：本期只实现下表明确列出的内容。未列出的能力一律不属于本期。

| 编号 | 能力或场景 | 完成边界 |
| --- | --- | --- |
| CR-IN1 | Case 执行需求 | Case 支持 executor、interaction、capabilities、resourceProfile 与 leaseScope |
| CR-IN2 | Workflow 资源快照 | 发布版本按可执行节点固化执行需求并校验目标系统兼容性 |
| CR-IN3 | 运行时 ResourceClaim | Task 就绪后生成、租赁、续约、释放和超时回收 |
| CR-IN4 | Execution Provider SPI | 实现 Container Provider 与现有 Windows Agent/Airtest Provider |
| CR-IN5 | Worker/Agent 术语拆分 | 固定 Dispatcher Worker 与动态 Environment Agent 分离，旧 Worker 注册数据兼容迁移 |
| CR-IN6 | 负载驱动并行 | 删除新任务的进程/设备并发输入，按 Claim 与实时容量调度 |
| CR-IN7 | 资源与队列页面 | 展示计算节点、交互目标、运行实例、等待 Case 和稳定阻塞原因 |
| CR-IN8 | 环境与 Agent 目录 | 一台 VM/Node/设备宿主机一条 Environment；Agent 注册会话、心跳和资源清单 |
| CR-IN9 | Automation Driver SPI | Airtest Adapter 覆盖 Windows、Android、iOS，统一执行规格、失败分类和证据 |
| CR-IN10 | Playwright Web Driver | `playwright-web` 执行器、专用能力与队列，产出页面截图、Trace、浏览器日志和断言结果 |

## 6. 成功标准

| 编号 | 可验证结果 | 验证方式 | 对应流程/规则 |
| --- | --- | --- | --- |
| CR-S1 | Test Job 请求不包含资源模式、资源池、进程并发或设备并发，Case API 能返回执行需求 | API 与页面检查 | CR-R1、CR-R2 |
| CR-S2 | 发布 Workflow 后修改 Case 不影响既有发布版本的节点执行需求 | 发布前后读取快照并执行 | CR-R3 |
| CR-S3 | 混合 Workflow 的脚本 Case 在容器运行，UI Case 只在自身就绪期间占用 Windows Desktop | 真实执行与时间线核对 | CR-R4、CR-R9 |
| CR-S4 | 两台 Windows VM 执行 8 个并行 UI Case 时峰值为 2；脚本并行度根据计算节点负载自动变化 | 混合负载验收 | CR-R6、CR-R10 |
| CR-S5 | 同一桌面在并发竞争、Agent 失联和迟到回调下始终最多一个有效 Lease | 并发与故障注入 | CR-R8、CR-E4、CR-E5 |
| CR-S6 | 资源页能区分 Dispatcher Worker、Environment Agent、计算容量和交互目标，并能解释每个等待 Case | 浏览器与 API 验收 | CR-R7～CR-R11 |
| CR-S7 | 两个 Environment 分别注册 Agent 和 Desktop；停止并重启其中一个 Agent 后环境 ID 不变、会话更新且容量不重复 | Agent 生命周期验收 | CR-R13 |
| CR-S8 | Airtest Adapter 能为 Windows、Android、iOS 生成执行规格，未知平台稳定拒绝；Windows 实跑产出截图和 HTML 证据 | SPI 单测与真实 Windows 执行 | CR-R14 |
| CR-S9 | 仅启动 Airtest Agent 时 playwright-web 容量为 0；启动 Playwright Worker 后任务自动执行且容量准确 | 资源快照、真实 UI Task | CR-R16、CR-R17 |
