# TestForge 核心概念

## 1. 一条测试链路

```text
Project + Git Commit
  -> Case YAML + Case 脚本资源 + ExecutionRequirement
  -> Workflow 已发布拓扑
  -> Test Job
  -> Jenkins Deployment READY
  -> 内部 Execution / DAG Task / Attempt
  -> Worker 或 Environment Agent
  -> Result / Evidence / Report
  -> AI Diagnosis
```

## 2. 对象边界

| 对象 | 回答的问题 | 关键约束 |
| --- | --- | --- |
| Project | 测哪个代码库？ | 保存仓库与 Pipeline 关联，不拥有虚拟机 |
| Case | 验证一个什么原子行为？ | YAML-first；声明自己的脚本、参数和资源需求 |
| Workflow | Case 按什么依赖顺序执行？ | 强归属 Project；发布版本冻结 DAG 拓扑 |
| Test Job | 对哪个版本执行哪套测试？ | 固定 Project、Commit、Workflow 与目标系统 |
| Environment | 被测应用发布到哪里？ | 全局共享资源；一个 VM、模拟器或节点对应一个环境实例 |
| Worker | 谁消费并执行 Case？ | 固定控制面消费者；按 Runner 能力领取任务 |
| Environment Agent | 谁代表具体环境？ | 在环境中注册、探活并暴露可分配交互目标 |
| Attempt | 一次节点执行尝试发生了什么？ | 内部可靠性记录；用户仍以 Test Job 为主视角 |
| Report | 测试结论是什么？ | 由确定性结果和 Evidence 聚合 |
| AI Diagnosis | 失败可能是什么原因？ | 只给带证据建议，不覆盖 Report |

## 3. Case 与 Workflow

一个 Case 表达一个可独立判断的测试行为，通常绑定一个主入口脚本。入口脚本可以导入同一 Case 资源包内的辅助文件，但一个 Case 只有一个执行入口，避免平台无法判断应从哪里开始。

Case 保存后，引用它的 Workflow 无需逐个重新编辑；下一次创建执行时读取 Case 的当前有效定义并固化快照。已经排队、运行或结束的执行继续使用自己的不可变快照，不受后续编辑影响。

Workflow 只负责拓扑：哪些 Case 并行、哪些 Case 必须等待前驱成功或完成。它不替代 Case 的脚本内容，也不承担测试环境选择。

## 4. Test Job 与内部执行历史

Test Job 是用户创建、确认和查看的测试任务。它对应一个固定 Commit，不会因为重复执行而漂移到分支的新提交。

一次执行会在内部产生执行记录、DAG Task 和 Attempt，用于保存重试、租约和故障恢复历史。这些记录服务于可靠性和审计，不在主导航中形成另一套与 Test Job 竞争的业务对象。

## 5. 版本固化

创建 Test Job 时先选择“分支”或“Tag”，平台随后显示并固化解析到的 Commit 编号与提交描述。分支和 Tag 是选择入口，Commit 才是报告可复现的版本事实。

```text
选择 master
  -> 解析 c6792a4c8e31...
  -> 展示提交描述
  -> Test Job 保存完整 Commit
  -> Jenkins 必须检出同一 Commit
  -> Report 回显同一 Commit
```

## 6. Jenkins 与 TestForge

| TestForge | Jenkins |
| --- | --- |
| 选择 Project、Commit 和目标系统 | 管理 SCM、Jenkinsfile、Agent 和工具链 |
| 触发已绑定 Pipeline | 检出固定 Commit |
| 等待 BUILDING / READY / FAILED 回调 | 构建、打包、初始化和部署 |
| READY 后释放测试节点 | 返回 Endpoint、制品或环境关联信息 |
| 汇总测试与报告 | 不负责 Case 调度和报告判定 |

空白环境首次发布可传入 `INITIALIZE_ENVIRONMENT=true`，但初始化内容由被测项目自己的 Pipeline 定义。

## 7. Case 级资源调度

资源要求属于 Case，而不是整个 Test Job。一个 Workflow 可以先运行普通 HTTP Case，再只为后续 UI Case 租用交互环境。

| Case 类型 | 典型执行资源 | 调度特点 |
| --- | --- | --- |
| HTTP / 脚本 | `pytest-http` 脚本执行槽 | 同一主机可运行多个并发进程 |
| Web UI | `playwright-web` 浏览器执行槽 | 可按浏览器上下文和主机容量并发 |
| Windows UI | `airtest` + Windows 交互目标 | 一个独立桌面通常同时只运行一个输入会话 |
| Android / iOS | Airtest + 设备或模拟器 | 按真实设备槽租用，完成或异常后释放 |

调度器根据 Case 的 Runner、平台和能力集合寻找兼容资源；用户不在 Test Job 中手工指定 Worker 或填写一个无法兑现的并发数。

## 8. 可靠性口径

- MySQL 保存业务状态、事件和 Outbox，是唯一真相源。
- Redis Streams 负责至少一次派发；重复消息必须由数据库幂等吸收。
- Worker 通过租约和心跳证明自己仍拥有 Attempt。
- 租约过期后可以创建新 Attempt；旧 Worker 的迟到回调被稳定拒绝。
- 回调使用稳定业务键与载荷摘要区分重复和冲突。
- 取消、完成和超时竞争时只能有一个合法终态。

## 9. 报告与 AI

确定性报告先聚合 Case 结果、耗时、失败分类、重试和 Evidence。AI Diagnosis 在报告形成后读取同一批证据，返回分类建议、置信度和引用的 Evidence ID。

即使 AI Provider 不可用，测试结果、通过率和附件仍必须可查看；AI 失败不能把成功测试改成失败，也不能把失败测试改成成功。
