# TestForge 端到端演示

本指南用于跑通并证明完整链路：**从 Web Console 创建测试资产，固定 Git Commit，触发 Jenkins 真实发布，按 Case 需求分配执行资源，最后生成报告与 AI 证据诊断。**

## 1. 演示拓扑

```text
Windows Host
├─ TestForge API + Web Console
├─ MySQL / Redis / MinIO
├─ Jenkins Controller + Builder Agent
├─ Playwright Worker（平台 UI 自测，可选）
└─ Hyper-V / 独立桌面
   ├─ TF-WIN-A: Jenkins Agent + Airtest Worker + Skill Sandbox
   └─ TF-WIN-B: Jenkins Agent + Airtest Worker + Skill Sandbox
```

最小完整链路只要求一个兼容 Worker。双 Windows VM 用于证明 UI 测试不会争用同一桌面，并展示真实并行容量。

上图的 Skill Sandbox 是作者录屏使用的独立被测项目，不随本仓库公开。使用者可选择平台自身做 Playwright UI 自测，或接入自己的被测项目；使用自己的项目时，用其仓库、Jenkinsfile、Case 和脚本替换游戏示例。

## 2. 前置检查

| 检查项 | 通过条件 |
| --- | --- |
| 仓库 | TestForge 与本次选择的被测项目均可被 Jenkins 取得完整 Commit；平台自测可使用同一仓库 |
| 控制面 | API Health 为 `UP`，Web Console 可打开 |
| Jenkins | Multibranch Pipeline 可扫描项目分支，Builder Agent 在线 |
| 回调网络 | Jenkins Agent 和 Worker 可以访问 TestForge API |
| Redis | API 与所有 Worker 使用同一个 Redis 实例 |
| 测试环境 | 对应环境实例已登记；未启动时状态明确，不伪装为可用 |
| Worker | Runner 与能力上报正确，运行页容量与实际在线资源一致 |
| Evidence | 本地或对象存储后端可写，报告能够打开附件 |

## 3. 启动控制面

```powershell
# 在包含 scripts/ 的平台仓库根目录执行
.\scripts\start.ps1
```

需要让 VM 访问宿主服务时，不要继续使用回环地址。按[多虚拟环境并行验收](../../acceptance/virtual-environment-parallel/README.md)统一配置宿主机可达地址、Redis 和回调地址。

## 4. 启动 Jenkins

```powershell
docker compose -f .\infra\compose.jenkins.yaml up -d --build --wait
```

访问 <http://127.0.0.1:8082>，确认：

1. 本次被测项目已有自己的 Multibranch Pipeline；平台自测使用 TestForge Platform Pipeline；
2. Pipeline 从对应项目根目录读取 `Jenkinsfile`；
3. Builder 与部署节点在线；
4. `TESTFORGE_SCM_MIRROR_URL`、回调地址和部署节点变量已按当前环境配置；
5. Jenkins Credential 只保存在 Jenkins，不写入 Project 表单或 Git。

详细边界见[基础设施与 Jenkins](../../infra/README.md)。

## 5. 准备执行资源

### 5.1 Playwright Web Worker

平台 UI 自测使用 `playwright-web`。先安装 Worker：

```powershell
cd testforge-worker
python -m pip install -e .
```

根据当前网络设置 `TESTFORGE_GATEWAY_URL` 与 `TESTFORGE_REDIS_URL` 后启动：

```powershell
$env:TESTFORGE_RUNNER = 'playwright-web'
$env:TESTFORGE_STREAM = 'testforge:tasks:playwright-web'
$env:TESTFORGE_WORKER_ID = 'playwright-web-local'
$env:TESTFORGE_WORKER_CAPABILITIES = 'RUNNER_PLAYWRIGHT_WEB,WEB_UI,PLATFORM_WINDOWS'
$env:TESTFORGE_WORKER_CONCURRENCY = '2'
$env:TESTFORGE_GATEWAY_URL = 'http://127.0.0.1:8081'
$env:TESTFORGE_REDIS_URL = 'redis://:testforge_redis@127.0.0.1:6379/0'
$env:TESTFORGE_ARTIFACT_BACKEND = 'local'
python -m testforge_worker --serve
```

### 5.2 Windows Airtest 环境

每个独立桌面运行一个 Skill Sandbox 和一个 Airtest Worker。VM A、VM B 的 Worker ID、Device ID 和 Environment ID 必须不同；Gateway、Redis 与对象存储必须指向同一套 TestForge 环境。

完整变量与双机验收见[多虚拟环境并行验收](../../acceptance/virtual-environment-parallel/README.md)。

## 6. 通过 Web Console 创建测试链路

以下步骤只通过浏览器完成业务操作；终端只用于启动基础设施、Jenkins 和 Worker。

### 6.1 登记环境实例

1. 打开“环境资源”。
2. 为每个 VM、模拟器或自测 Host 建立一个环境实例。
3. 选择平台系统，并填写与 Jenkins 部署契约一致的发布键。
4. 保存后核对 Agent 和交互目标是否绑定到正确实例。
5. 已关机的 VM 应显示不可用，并提供明确启动入口或运维提示。

环境是全局共享资源，不归 Project 所有；Test Job 只声明目标系统，平台在执行时自动选择兼容环境。

### 6.2 创建被测 Project

1. 打开“被测项目”，点击“新建”。
2. 填写名称、Git 仓库和默认分支。
3. 保存 Project。
4. 核对页面读取到的 Jenkins Pipeline 目录。

Project 编码由系统生成并隐藏；Jenkins 地址、Provider 类型和 Folder 属于平台 Connection，不应出现在 Project 业务表单中。

### 6.3 创建 YAML-first Case

1. 在 Project 的 Case 区点击“新建 Case”。
2. 上传该 Case 自己的 Python、Airtest `.air` 或 ZIP 资源。
3. 上传成功后确认资源 URI 已自动写入 YAML。
4. 校验 `execution.executor`、`interaction`、`capabilities` 与目标平台。
5. 点击“校验 YAML”，再保存 Case。

一个 Case 有一个主入口；ZIP 可以包含入口及其辅助模块，但不能包含多个无法判定的独立入口。删除右侧资源并保存后，当前 Case 定义同步移除引用；已经创建的执行快照不受影响。

### 6.4 创建 Test Job 与 Workflow

1. 打开“测试任务”，点击“新建”。
2. 选择 Project，填写面向人的任务名称和说明。
3. Workflow 默认选中该 Project 最近发布的版本；需要新流程时点击下拉框右侧“新建并编辑 Workflow”。
4. 在全屏工作台从左侧 Case 库加入节点，连接依赖边，保存草稿并发布绑定任务。
5. 在版本选择器的“分支”或“Tag”页选择版本。
6. 核对解析出的 Commit 编号和提交描述。
7. 选择目标系统和优先级，保存草稿并确认任务。

Test Job 不填写任务 UUID、Worker、具体 VM 或并发数；这些信息由系统生成或根据实际容量决定。

## 7. 执行并观察

1. 在已确认 Test Job 上点击执行。
2. 打开“运行与报告”。
3. 先观察“执行资源与队列”：等待发布、待调度、执行中、脚本执行槽和 UI 测试机数字应与真实状态一致。
4. Jenkins 收到固定 Commit 后进入 BUILDING；发布完成回调 READY。
5. READY 后 DAG 节点按依赖释放，普通脚本和 UI Case 分别进入兼容队列。
6. Worker 领取 Attempt、续租、执行并回传结果与 Evidence。

如果任务长时间排队，先看等待原因和能力容量，不要通过修改数据库或直接调用接口绕过状态机。

## 8. 查看报告

在任务行点击“查看报告”，核对：

- Test Job、Commit、Workflow 版本与 Jenkins 实际检出一致；
- DAG 节点、依赖边和状态可读；
- Case 结果、耗时、执行 Worker、重试和失败分类完整；
- Playwright 截图、Trace、浏览器日志或 Airtest 截图可访问；
- 确定性报告先形成，AI Diagnosis 后生成；
- AI 引用存在的 Evidence ID，且不改变通过率与终态。

## 9. 完成判定

| 编号 | 验收点 | 通过标准 |
| --- | --- | --- |
| E2E-1 | 版本一致 | UI、Test Job、Jenkins 和 Report 显示同一完整 Commit |
| E2E-2 | 发布真实 | Jenkins 确实构建并部署，不由 TestForge 假造 READY |
| E2E-3 | 资源匹配 | Case 只被兼容 Runner/平台/能力执行 |
| E2E-4 | 流程正确 | DAG 依赖按边释放，失败与阻断可区分 |
| E2E-5 | 证据完整 | 每个执行结果可追溯到日志或附件 |
| E2E-6 | 报告稳定 | 刷新或 SSE 重连后页面与持久化终态一致 |
| E2E-7 | AI 有边界 | AI 失败不影响确定性报告；成功建议含有效引用 |
