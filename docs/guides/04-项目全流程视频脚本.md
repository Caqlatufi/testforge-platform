# TestForge 项目全流程视频脚本

## 1. 视频定位

| 项 | 设定 |
| --- | --- |
| 目标时长 | 12～15 分钟 |
| 目标观众 | 测试开发、后端、DevOps、开源项目使用者 |
| 核心问题 | TestForge 如何保证“测的是明确版本、跑在正确资源上、结果可追溯” |
| 叙事主线 | Project → Case → Workflow → Test Job → Jenkins → Worker → Report → AI/MCP |
| 演示项目 | Skill Sandbox；结尾补充 TestForge 自测 |

视频不要从技术栈列表开始。先用一次真实任务建立问题，再逐层解释为什么需要这些模块。

## 2. 录制前准备

- 关闭系统通知、聊天窗口和密码管理器弹窗。
- 浏览器缩放固定为 100%，窗口至少 1440×900。
- 清理任务列表中的乱码、临时数据和无关失败记录。
- 准备一个已完成任务作为报告兜底，同时新建一个任务展示实时过程。
- Jenkins、API、Web Console、Redis、MinIO 和两个 VM 预先启动并完成健康检查。
- 确认画面不会出现 Token、内网凭据、用户主目录或私有仓库地址。
- AI Diagnosis 可能等待较久，预先生成一份成功结果；录制时说明异步生成，不剪辑成同步瞬间完成。
- 准备一张架构图和一张关键对象链路图，均使用仓库现有 Mermaid 导出。

## 3. 完整分镜与文案

### 0:00–0:35 开场：这不是一个脚本启动器

**画面**：先展示“运行与报告”列表，再快速切到某个成功任务的 DAG 和 Evidence。

**口播**：

> 这是 TestForge，一个把被测版本发布、测试编排、执行资源和结果证据连起来的自动化测试平台。很多工具能运行脚本，但真实团队更难回答的是：测的到底是哪一个 Commit，环境是否真的发布成功，UI 用例有没有拿到正确测试机，以及 Worker 掉线或回调重复后，这份报告还能不能相信。接下来我会用一个 3D 桌面小游戏，完整跑一遍这条链路。

**字幕关键词**：固定 Commit / 真实发布 / Case 级调度 / 确定性报告。

### 0:35–1:30 架构与职责边界

**画面**：展示根 README 的系统全景图，依次高亮 Web、TestForge API、Jenkins、Worker、Environment、Report、MCP。

**口播**：

> TestForge 管理的是测试意图和执行状态。Jenkins 仍然负责 SCM、构建和真实部署；Worker 负责运行 Case；MySQL 保存业务真相，Redis Streams 只负责至少一次派发；报告先由确定性结果生成，AI 只能基于证据给建议。旁边的 Skill Sandbox 是独立被测项目，它不引用平台代码，所以这不是把 Demo 逻辑写死在测试平台里。

**转场句**：

> 先从用户真正关心的四个对象开始：Project、Case、Workflow 和 Test Job。

### 1:30–2:35 被测 Project：代码与 Pipeline 的边界

**画面**：打开“被测项目”，选择 Skill Sandbox；展示名称、Git 仓库、默认分支和 Pipeline 目录。

**口播**：

> Project 表示一个被测 Git 项目。这里不再让用户填写 Jenkins 地址、CI 类型或 Folder，因为这些属于平台级连接。Project 只保存仓库和可用 Pipeline 关联。每个项目在自己的仓库维护 Jenkinsfile，TestForge 不创建 Jenkins Job，也不替 Jenkins 执行部署。

**画面检查**：不要展示本机绝对路径；公开录制时使用已脱敏的仓库 URL。

### 2:35–4:00 YAML-first Case：测试原子能力

**画面**：选择一个已有 Case，展示 YAML 编辑器、右侧脚本资源、执行器和能力声明；再快速演示“新建 Case → 上传 → 自动写入资源 URI → 校验 YAML”。

**口播**：

> Case 是最小可判断的测试行为。它用 YAML 同时描述参数、执行入口和资源要求。右侧资源只属于当前 Case，上传后自动写入 YAML，删除后保存也会移除引用。一个 Case 只有一个主入口，但 ZIP 内可以包含它依赖的辅助模块。这里把资源声明放在 Case，而不是 Test Job，因为同一个工作流里，只有某些节点可能需要浏览器或独占桌面。

**补充口播**：

> Case 保存会影响后续执行；已经排队、运行或完成的执行使用自己的快照，不会被回写修改。

### 4:00–5:35 创建 Test Job 与选择版本

**画面**：打开“测试任务”，点击“新建”；选择 Skill Sandbox，填写名称；展示 Workflow 默认值；打开版本选择器，在“分支”和“Tag”间切换，最后选中一个分支。

**口播**：

> Test Job 是用户真正创建和追踪的测试任务。项目选中后，平台默认选择最近发布的 Workflow。版本选择器参考常见 CI 产品分为分支和 Tag，但选中后都会解析成明确 Commit，并展示提交描述。任务保存的是这个 Commit，而不是会继续移动的分支名。

**口播强调**：

> 页面不要求填写任务 UUID、具体 VM 或并发数。UUID 由系统生成，机器由调度器按 Case 能力和实时负载分配，并发不能靠用户随便填一个数字承诺。

### 5:35–7:05 Workflow：只编排依赖，不复制 Case

**画面**：点击 Workflow 下拉右侧“新建并编辑 Workflow”，进入全屏二级工作台；从左侧滚动 Case 列表拖入两个或三个节点，连接 `ON_SUCCESS` 边，保存并发布绑定任务。

**口播**：

> Workflow 是项目内的 DAG。DAG 的含义是有方向、无环：边表达先后依赖，但任何路径都不能回到自己。Case 保存测试内容，Workflow 只保存拓扑，所以不再额外引入一个和 Workflow 含义重叠的 Suite。发布时先保存当前画布，再发布这个版本并回填任务，避免用户看到的图和服务端快照不一致。

**画面提示**：主页面不滚动；左侧节点库独立滚动。确保连线清晰可见。

### 7:05–8:00 环境资源：系统类型自动分配

**画面**：打开“环境资源”，展示 TF-WIN-A、TF-WIN-B 的启停状态、Agent 与交互目标；再回到任务页展示只选择目标系统。

**口播**：

> 环境是全局共享资源，一个 VM、模拟器或节点对应一个环境实例。任务只选择 Windows 这样的目标系统，不直接绑定某台机器。真正执行时，平台根据在线 Agent、交互目标和 Case 能力自动分配。空闲 VM 可以关机节省资源，需要时再由环境页启动。

### 8:00–9:30 执行与 Jenkins 真实发布

**画面**：确认并执行任务；并排或切换到 Jenkins Build，展示参数中的完整 Commit、BUILDING、Deploy、READY；回到运行页观察“等待发布 Case”归零。

**口播**：

> 执行开始后，TestForge 先预占合适环境并触发 Jenkins。Jenkins 校验完整 Commit，检出对应代码，构建并部署到测试环境，然后回调 READY。只有 READY 以后，DAG 节点才进入测试队列。发布失败会明确阻断任务，不会被伪装成产品断言失败。

**可选补充**：

> 如果是空白环境，TestForge 可以一次性传入初始化标记，但初始化逻辑仍由项目自己的 Pipeline 负责。

### 9:30–10:45 Case 级资源调度与实时状态

**画面**：展示单行五指标；展开 Agent/交互目标；进入任务详情看 DAG 节点从 QUEUED 变为 RUNNING、SUCCEEDED。

**口播**：

> 这里按真实能力显示容量：等待发布、待调度、执行中、脚本执行槽和 UI 测试机。普通脚本可以在一台机器上并发，Windows UI 测试受独立桌面限制。调度器不会把 Airtest Worker 算进 Playwright 容量，也不会因为页面填了并发数就创造不存在的机器。

**补充口播**：

> Redis 消息允许重复到达，最终由数据库状态、Attempt 版本和租约吸收重复。Worker 丢失后新 Attempt 可以接管，旧 Worker 的迟到结果不能覆盖新结果。

### 10:45–12:15 报告、证据与 AI 诊断

**画面**：任务行点击“查看报告”；展示版本摘要、Workflow 运行图、节点时间线、结果表、截图或 Trace，再展示 AI Diagnosis。

**口播**：

> 报告页仍以 Test Job 为主视角，内部执行次数和 Attempt 只用于解释重试历史。这里可以核对 Commit、Workflow、每个 Case 的状态、耗时、Worker、失败分类和 Evidence。先形成确定性报告，再触发 AI 诊断。AI 的每条建议必须引用存在的 Evidence；即使 Provider 不可用，测试终态和通过率也不会变化。

### 12:15–13:20 TestForge 测试 TestForge

**画面**：切到 TestForge Platform Project，展示 Playwright Case、一次平台 UI 自测报告，以及截图/Trace。

**口播**：

> 平台也把自己当成普通被测项目。Jenkins 发布一套独立 TestForge 测试环境，Playwright Worker 只能通过浏览器完成导航、创建和查看操作，不能用 REST 代替 UI 步骤。这可以暴露页面路由、加载状态、按钮可用性和真实交互问题，同时避免测试直接污染开发实例。

### 13:20–14:10 MCP：让 AI 使用平台，而不是绕过平台

**画面**：展示 `testforge-mcp` README、MCP Host 配置和工具列表；如环境稳定，演示查询当前工作区或读取报告。

**口播**：

> TestForge 还提供独立 Go MCP Server。它运行在 AI 客户端侧，只读取用户授权的 Git 工作区，并通过公开 API 创建 Case、Workflow、任务和查询报告。MCP 不直连数据库，也不把 AI 生成内容直接当成测试结论；版本、幂等和状态机仍由 TestForge 控制。

### 14:10–14:45 收束

**画面**：回到系统全景图，再切到 GitHub README 的文档入口。

**口播**：

> 总结一下，TestForge 解决的不是单个脚本怎么启动，而是一次测试如何从明确 Commit 出发，经过真实发布、可靠调度和证据回传，最终形成可复现报告。仓库包含完整设计文档、自动化测试、验收证据和 Skill Sandbox 示例。如果你想运行或参与项目，可以从 README 的五分钟启动和端到端指南开始。

## 4. 60 秒短版文案

> 自动化测试最难的不是把脚本跑起来，而是证明测的是哪个 Commit、环境是否真的发布成功、Case 有没有拿到正确资源，以及 Worker 掉线后结果还能不能信。TestForge 用 Project、YAML Case、Workflow DAG 和 Test Job 固化测试意图；由 Jenkins 真实发布被测版本，再按 Case 的能力要求把普通脚本、Playwright 或 Airtest 分配给兼容 Worker。MySQL 保存状态真相，Redis Streams 负责至少一次派发，租约和幂等回调处理宕机与重复。最后，平台聚合截图、Trace、日志和结果形成确定性报告，AI 只基于证据给建议。它甚至可以用 Playwright 测试自己的 Web Console，并通过 Go MCP 接入 AI 客户端。完整代码、设计和演示都在仓库里。

## 5. 录制失败时的降级方案

| 失败 | 现场处理 | 不应做的事 |
| --- | --- | --- |
| Jenkins 构建耗时 | 展示已触发的新 Build，再切换到预先完成的同 Commit 报告 | 剪辑成 TestForge 自己完成部署 |
| VM 启动慢 | 先展示环境为启动中，再用已在线的一台 VM 完成单机流程 | 把离线环境标为可用 |
| AI Provider 超时 | 展示确定性报告和“AI 不可用”降级，再打开预生成诊断解释格式 | 把 AI 输出冒充确定性结论 |
| SSE 中断 | 刷新或重连，说明事件持久化和游标续传 | 直接改数据库状态 |
| 新任务失败 | 保留失败现场，打开 Evidence 解释定位，再切到成功任务完成后续章节 | 隐藏错误并宣称全链路通过 |

## 6. 发布前检查

- 口播中的对象名称与页面一致：Test Job 是用户主对象，Attempt 是内部历史。
- 不再提 Suite、独立 Runs 主栏或 Python CLI。
- 不展示真实凭据、绝对用户路径、私有仓库地址和未经脱敏的 Evidence。
- 所有“已通过”表述都有当前 Commit 对应的真实证据。
- 视频简介附上 README、快速开始、端到端指南和 MCP 文档链接。
